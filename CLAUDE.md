# Rimwatch

An original game of rescue modes for the iPhone Duo's inner display; its first mode, Ridgeline,
is a side-scrolling rescue shooter. Native iOS, Swift,
SpriteKit, no third-party dependencies, no asset files (art drawn in code, sound synthesised).

It is growing into three modes in one world (Ridgeline, the first game built; Redoubt, a
twin-stick arena shooter, being built now; then Riftwing) and later a campaign. See "Expansion" in `PLAN.md`. Stop at each gate in
the progress list, and write a mode's design into the plan for approval before building it.

## Start here

Read `PLAN.md`. Its **Progress** checklist says what is done. Continue from the first unticked item,
and tick items as they are built and verified.

## Rules

- This is an original game. Do not copy the name, sprites, sounds, enemy names or screen layout of
  any existing game.
- Gameplay only runs on the open inner display. When the phone is closed the game pauses and the
  outer display shows the pause menu (start over, end game, options, high scores). See
  "Fold behaviour" in `PLAN.md`.
- `GameCore/` is a plain Swift package with no UIKit or SpriteKit imports, in three targets:
  `GameCore` (shared by every mode; knows nothing about any one mode), `RidgelineCore`
  (Ridgeline's game logic) and `RedoubtCore` (Redoubt's). A mode's target never imports another
  mode's. Game logic knows entity roles, never their appearance; appearance comes from the
  mode's theme (`Theme` for Ridgeline, `RedoubtTheme` for Redoubt). One library product,
  `GameCore`, carries every target, so the Xcode project links a single product; a new mode's
  target is added to that product.

## Building and testing

- Game logic: `swift test` inside `GameCore/`. Works with Xcode closed. The tests use Swift
  Testing, which the Command Line Tools alone don't provide. If `import Testing` fails, run
  `DEVELOPER_DIR=/Applications/Xcode.app/Contents/Developer swift test`, or switch `xcode-select`
  to Xcode.
- Difficulty numbers were tuned against scripted bots. After changing a mode's `Tuning.swift` or
  `WaveDirector.swift` (in `GameCore/Sources/RidgelineCore/` or `GameCore/Sources/RedoubtCore/`),
  re-run the harness in `Tools/Harness` as well as the tests. Ridgeline is its default; a leading
  `redoubt` argument runs Redoubt's bots (usage in `PLAN.md`).
- The app icon is generated by `Tools/Icon` from the emblem in
  `GameCore/Sources/GameCore/Emblem.swift`, which the title screen also draws. Never edit
  `AppIcon.png` by hand; re-run the generator (command in `README.md`) after changing the emblem.
- `#expect` cannot wrap a mutating call. Write `#expect(session.resume() == true)`, not
  `#expect(session.resume())`.
- The app is a shell plus modes. `Rimwatch/Shell/` is shared by every mode and must not import
  a mode's package target or name its types; `Rimwatch/Modes/ModeRegistry.swift` lists the modes
  and is the only shell-level file that names one. `ModeHost` drives the session through the
  shared `ModeFrontEnd`/`ModeSession` (`GameCore/Sources/GameCore/Session/`, generic over a
  mode's run; Ridgeline calls them `FrontEnd`/`GameSession`). A mode implements `GameMode`
  (`Shell/GameMode.swift`), reads the live session through the closure it is given, never steps
  its run itself, and reacts to the events the host passes it.
  Gameplay numbers live in each mode's `Tuning.swift` (`GameCore/Sources/RidgelineCore/`,
  `GameCore/Sources/RedoubtCore/`). A mode's app code lives in `Rimwatch/Modes/<Mode>/` and
  never reaches into another mode's folder.
- Verify in proportion to the change. A change inside one mode's package target and its
  `Rimwatch/Modes/<Mode>/` folder needs that mode checked, plus the package tests. A change to
  `Rimwatch/Shell/` or the shared `GameCore` target needs every mode checked.
- To check that a shell change did not alter behaviour, compare DEBUG logs of two builds launched
  with `-hinge open -autopilot <skill> -seed <n> -fixedFrame -logFeedback -resetSettings`: the
  `[Rimwatch run]`, `[Rimwatch screen]` and `[Rimwatch feedback] haptic` lines are identical line
  for line for the same build (the `[Rimwatch audio]` lines are not deterministic). Add
  `-mode redoubt` to do the same for Redoubt; `-autopilot` takes `idle`, `novice`, `competent`
  or `shooter` in both modes (Redoubt's `shooter` never rescues, so it reaches the power cut:
  seed 7, wave 8).
- DEBUG `-mode <id>` loads a mode at launch (`ridgeline`, `redoubt`). `-debugSecondMode` lists
  Ridgeline again as "Ridgeline B"; it dates from when only one mode existed.
- `FrontEndReplayTests` is a golden replay of a whole session. If it fails after a refactor, the
  refactor changed behaviour: fix the code, not the expected values. Re-capture the values only
  after a deliberate gameplay change (the test prints a `REPLAY` summary for that).
- The app: build, run and test through the Xcode MCP server (`xcode`, added with
  `claude mcp add --transport stdio xcode -- xcrun mcpbridge`). The project must be open in Xcode.
  If the `xcode` tools are missing, check `claude mcp list` and the "Prerequisites" in `PLAN.md`
  before falling back to `xcodebuild`.
- Xcode's DeviceInteraction MCP tools drop their sessions here ("Session not found"). Run and
  screenshot with `xcrun simctl` instead, and build with `xcodebuild` when the MCP build tools
  are not enough.
- The iPhone Duo simulator needs its own runtime build (see "Progress" in `PLAN.md`). It boots
  closed and cannot be unfolded from the command line, so fold behaviour is tested on an ordinary
  iPhone simulator with the DEBUG launch argument `-hinge open|closed|none` and the Darwin
  notifications listed in `PLAN.md`. Never use `simctl io ... screenConfig` on it.
- The iPhone Duo SDK and simulator need Xcode 27.1 or later. The Duo API names in `PLAN.md` are
  secondhand; confirm them against the installed SDK before using them.
